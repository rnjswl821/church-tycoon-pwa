# 목양타이쿤 (church-tycoon-pwa)

교회를 세우고 성도를 섬기며 함께 성장시키는 경영 시뮬레이션 게임. 상점이 아니라 **교회 그
자체**(예배당·교육관·친교실·주차장)를 짓고, 사역자·직분자를 세우고, 사역(새벽기도·소그룹·
어린이부 등)을 운영하며 성도수·신앙지수·지역신뢰를 함께 키워가는 턴제(주 단위) 게임이다.

- 최초 작성: 2026-08-25 / 2차 개정: 2026-08-25(같은 날, 오너 실사용 피드백 대량 반영)
- 작성: master (직접 구현)
- 플랫폼: PWA(설치 가능한 웹앱, 오프라인 동작) — 순수 HTML/CSS/JS, 빌드 도구·의존성 없음
- 뽑기·확률형 수집 요소 없음(성취/선택 기반), 실제 화폐 결제 연동 없음(섬김기금은 KRW 단위로
  "표시"만 되는 인게임 재화 — 실제 결제·송금과 무관)

## 게임 컨셉

상점을 운영하는 타이쿤이 아니라 **교회 자체를 운영·성장**시킨다(오너 확인, 2026-08-25).

### 핵심 루프 (매주)
1. 성도수 × 신앙지수 기반으로 "섬김기금"(원화 단위) 수입 발생, 사역·인건비 지출
2. 신앙지수·지역신뢰가 활성 사역·건물·사역자·직분자 효과에 따라 오르내림
3. 지역신뢰·건물·사역자 효과로 새가족 유입, 정착률에 따라 이탈(교회를 옮김) 발생
4. **최소 4주(게임 속 한 달) 간격 + 그 이후 매주 40% 확률**로 20종 중 하나의 선택형 내러티브
   이벤트 발생(평균 약 5.5주 간격 — "대략 한 달에 한 번" 리듬, 오너 지시 2026-08-25) —
   **선택지 4개, 효과는 비공개**(선택 전 결과를 알 수 없다 — 매 선택이 신중한 트레이드오프가
   되도록 모든 선택지가 오르는 값과 내리는 값을 함께 갖는다). 선택 직후 실제 변화량을 결과
   화면에서 공개한다.
5. 성도수 임계값(30/100/300/800)을 넘으면 교회 성장 단계(씨앗→새싹→열매→든든한→축복의) 승급,
   최고 단계 도달 시 플레이 기록(주차·최종 스탯·건물·직분자 수)을 정리한 엔딩 화면이 뜬다
   (엔딩 후에도 계속 플레이 가능 — 게임오버 아님)

### 리소스
- 섬김기금(원화 단위 표시, 실제 결제 연동 없음) · 성도수 · 신앙지수(0~100) · 지역신뢰(0~100)
  · 봉사자수
- 건물: 예배당(정원)·교육관(신앙·정착)·친교실(신뢰·봉사자)·주차장(유입)
- 사역자(유급 청빙): 부목사·찬양리더·교육부장·전도팀장 — 청빙비 + 주당 사례비, 재정 형편이
  안 되면 "내보내기"로 되돌릴 수 있다
- 직분자(무급 임직 — 고신헌법 근거, 아래 절 참조): 장로·집사·권사
- 사역: 새벽기도·소그룹모임·어린이부·청년부·봉사단 (주당 유지비, 일부는 조건 해금)
- 행사: 부흥회·전도축제·여름수련회 (1회성 섬김기금 소모로 즉각 효과)

### 방치 페널티 (5차, 2026-08-25 — 오너 지시)
"가만히 두기만 하면 서서히 좋아지지 않도록" — 활성 사역·사역자·직분자가 **단 하나도 없는**
주(게임 시작 후 3주 유예 후 적용)에는: ①방치 관리비로 수입의 150%가 추가로 빠져나가
순수입이 항상 마이너스가 되고(재정위기 안전장치와 맞물려 기금이 0 근처에 머문다), ②새가족
자연 유입이 완전히 끊기고(0명), ③이탈률이 평소보다 훨씬 높아진다. 새벽기도(주당 5만원)
하나만 켜도 즉시 해제된다 — 최소한의 능동적 관리를 강제하되 회복 불능은 아니다. 100주
방치 시뮬레이션으로 성도 12명→0명, 신앙지수·지역신뢰 0까지 실측 확인(아래 검증 절 참조).
반대로 사역을 꾸준히 관리하는 플레이는 이 페널티의 영향을 전혀 받지 않는다(501주
시뮬레이션 결과 불변 확인).

### 재정 위기 처리 (자동 안전장치)
3주 연속 섬김기금이 마이너스면 ①가장 유지비가 큰 활성 사역을 먼저 중단하고, 그래도 계속
적자면 ②가장 사례비가 큰 사역자를 내보낸다(순서: 사역 → 사역자 — 무급 직분자는 대상 아님).
**이 2단계 안전장치 덕분에 아무리 나쁜 재정 판단을 반복해도 게임이 영구적으로 막히지 않는다**
— 200~500주 시뮬레이션으로 실측 확인(아래 검증 절 참조).

## 경제(원화) 밸런스 — 출처와 한계를 함께 밝힌다

오너 요청("실제 한국 원화 단위와 시세로")에 따라 웹서치로 2025~2026년 국내 교회 시세를
조사해 반영했다:

- **부목사 사례비**: 정재영 박사 통계 기준 전체 평균 월 158만원, 목회데이터연구소 기준 표준
  희망 사례비 월 303만원, 대형교회는 월 350~500만원 — 이 게임은 부목사 월 250만원(주급
  환산 58만원)으로 그 중간대를 채택했다. [출처: 복음과상황 "2025년 목회자 표준 사례비
  대화모임"](https://www.goscon.co.kr/news/articleView.html?idxno=41942)
- **교회 건축공사비**: 평당 500~600만원이 보편적 시세, 소형/컨테이너 건축은 평당 200만원까지
  낮아질 수 있음. [출처: 김신김 건축사사무소 "2026년도 용도별 평당 공사비"](https://kimshinkim.com/%EC%9A%A9%EB%8F%84%EB%B3%84-%ED%8F%89%EB%8B%B9-%EA%B3%B5%EC%82%AC%EB%B9%842026%EB%85%84%EB%8F%84-%EC%B5%9C%EC%8B%A0/),
  [에이코드건축사사무소 "2026년 용도별 평균 건축비"](https://www.acode-architects.com/news/yongdobyeol-pyeongdan-geonchukbi-2026/)
- **건축비 재조정(중요)**: 이 평당 단가로 예배당 확장비를 처음 역산했더니(정원 증가분 ÷
  1인당 필요 평수 × 평당 단가) 레벨1 확장에만 9천만원이 나왔고, 시뮬레이션 검증 결과
  **첫 확장까지 100주 이상 걸려 사실상 게임이 진행되지 않는 문제**가 발견됐다(성도 40명
  고정 시 주간 순수입이 약 60~80만원 수준이라 9천만원을 모으는 데 100주+ 소요). 그래서
  건축비는 "억 단위의 realistic한 느낌"은 유지하되, 정확한 평당 단가 역산은 포기하고
  플레이 가능한 속도로 낮췄다(레벨1 예배당 1,200만원 등 — 아래 검증 절의 재시뮬레이션 결과
  참조). **한 문장 요약: 사례비는 실측 시세 그대로, 건축비는 "실측 시세를 참고해 억 단위로
  느껴지되 진행 가능하게 튜닝한 근사치"다.** 정밀한 회계 시뮬레이터가 아니라 게임이므로
  이 절충을 명시적으로 밝혀 둔다.
- 섬김기금 수입 공식(성도당 주간 헌금)도 실제 통계가 아닌 게임 밸런스 추정치다(신앙지수에
  따라 주당 8,000~20,000원/인) — 정확한 헌금 통계는 조사하지 않았음을 밝힌다.

## 직분자 임직 — 고신총회 헌법 근거 (2026-08-25 추가)

오너 요청으로 실제 `04 지원/00 자비스/01 행정팀/고신헌법 1부 교리표준_전문.md`,
`고신헌법 2부 관리표준_전문.md`(대한예수교장로회 고신총회, 노회 결의로 개정되는 공식
헌법 문서)를 직접 읽고 다음 조항을 근거로 반영했다:

- **장로**: 40세 이상 66세 미만 세례교인, 등록 3년 이상(2부 제65조) · 공동의회 2/3 이상
  득표로 선출(제67조) · 5개월 이상 교육+노회 고시 합격 후 임직(제68조)
- **집사**: 35세 이상 66세 미만, 등록 2년 이상(제75조) · 선출·임직 절차는 장로에 준함
  (제77~78조)
- **권사**: 45세 이상 66세 미만 여성, 등록 2년 이상(제81조) · 절차는 집사에 준함(제83~84조)
- **당회**: 시무목사+시무장로로 구성. 장로 1명=준당회, 2명 이상=완전당회(제108조). 세례교인
  30명 이상이어야 조직 요건 충족(제109조)

게임에서는 이 요건(연령·기간별 개인 추적)을 단순화해 "성도수 30명 이상 → 장로 임직 해금",
"봉사자 5명 이상 → 집사/권사 임직 해금"으로 근사했고, 임직마다 봉사자 인원(후보로 세울
사람)과 소정의 비용(교육·고시 실비)을 소모한다. 장로 2인째 임직 시 "완전당회 구성" 마일스톤이
뜬다. **권징(재판·시벌·출교 등 사법 절차, 2부 III장)은 의도적으로 게임 소재에서 제외했다** —
민감한 실제 교회 사법 영역을 오락 콘텐츠로 다루는 것은 부적절하다고 판단했다.

## 픽셀아트 비주얼

대시보드 상단에 항상 떠 있는 탑뷰(위에서 내려다본 시점) 캠퍼스 씬. 건물 레벨이 오르면
스프라이트가 실시간으로 바뀌고, 사람 스프라이트가 경내에서 각자 다른 리듬으로 서성인다.
주차장이 포장된(레벨 1 이상) 뒤로는 방문 차량이 약 22초 주기로 진입로를 타고 들어와 잠시
주차했다 나가기를 반복한다. 건물을 탭하면 해당 관리 탭으로 이동한다.

- **인원 표현 축척(오너 지시, 2026-08-25 3차)**: 사람 스프라이트 1명 = 성도 10명. 정상
  크기 격자는 24칸(=최대 240명)까지고, 그 이상이면 **자동으로 절반 크기·더 촘촘한 77칸
  격자로 전환**해 최대 770명까지 담는다(그 이상은 "+N명 더" 배지). 42/250/1,000명 세
  구간에서 스프라이트 수·크기 전환·오버플로 숫자를 헤드리스 스크린샷+타이틀 출력으로
  직접 계산 검증했다(예: 1,000명 → 77칸 만석(770명 표시) + "+230명 더").

- 모든 스프라이트는 `tools/gen_sprites.py`(Python + Pillow)로 **절차적으로 직접 그린** 것 —
  외부 이미지·에셋팩·AI 이미지 생성 API 미사용, 라이선스 이슈 없음. 다시 만들거나 늘리려면
  이 스크립트를 고쳐 `python3 tools/gen_sprites.py`만 재실행하면 `assets/`가 재생성된다.
- 예배당 6단계(작은 예배소 → 종탑·스테인드글라스 대성당)·교육관 5단계·친교실 5단계(차양·야외
  테이블)·주차장 4단계(자갈 → 포장+차량)·방문 차량 3색을 레벨별로 그렸다.
- 사람 애니메이션은 상태 저장 없이 `tMs`(타임스탬프)만으로 매 프레임 재계산되는 순수 함수다
  (개인별 다른 주기·위상의 사인파 서성임 + 이동 방향에 따른 좌우 반전). 방문 차량도 동일하게
  `tMs % 22000` 기반 결정론적 진입→주차→퇴장 사이클이라 일시정지·프레임 드롭에 안전하다.
- 폰트: 숫자·영문 라벨은 Google Fonts "Press Start 2P"(픽셀 폰트), 한글 본문은 시스템 폰트.

## 실제 폰 UI + 타이쿤 게임 관례 (2026-08-25 2차 개정)

오너 피드백("화면 밖에 버튼 내놓지 말고", "실제 타이쿤 게임 참고") 반영:

- **폰 프레임 고정**: `#app`이 항상 최대 430px 폭의 "폰 화면"으로 렌더링되고 데스크톱 넓은
  창에서는 중앙에 카드처럼 떠 있다(모달도 이 폭 안에서만 뜬다). 320~430px 전 구간에서 스탯
  5칸·하단 버튼이 절대 화면 밖으로 안 나가도록 아이프레임 격리 테스트로 실측 확인함(아래
  검증 절 참조).
- **자동진행 전용, 수동 "다음 주" 버튼 없음(5차, 2026-08-25)**: 오너 지시("시간이 알아서
  흐르니까 다음주 버튼은 없어도 될 것 같아")로 수동 진행 버튼을 아예 제거했다. 6초마다 자동으로
  다음 주로 진행하며, 이벤트/마일스톤 모달이 떠 있는 동안에는 절대 덮어쓰지 않고 대기한다.
  하단의 유일한 시간 컨트롤은 "⏸ 시간이 흐르는 중 / ▶ 일시정지됨" 토글 하나뿐이다(일시정지
  중엔 단일 스텝 진행 수단도 없다 — 재생을 눌러야 다시 흐른다).

## 공유용 아티팩트 배포 (6차, 2026-08-25)

`http://localhost:8934`는 이 컴퓨터 안에서만 열리는 주소라 카톡 등으로 공유해도 상대방
기기에서는 열리지 않는다(로컬호스트는 "자기 자신"을 가리키는 주소). 실제로 공유 가능한
링크가 필요해 `tools/build_artifact.py`로 `assets/*.png` 37개를 base64로 인라인하고
`style.css`·`scene.js`·`app.js`를 한 HTML 파일로 합쳐 Claude 아티팩트로 게시했다
(재빌드: `python3 tools/build_artifact.py`, 출력은 스크립트 안에 하드코딩된 스크래치패드
경로 — 재사용 시 출력 경로를 프로젝트 안으로 바꿔서 쓸 것).

- **아티팩트 버전의 한계**: 서비스워커(오프라인 캐시)·PWA 홈화면 설치는 되지 않는다(아티팩트
  샌드박스는 별도 오리진이라 `sw.js`를 등록해도 조용히 실패한다 — 게임 자체 동작에는 지장
  없음). 저장은 그 아티팩트 자신의 브라우저 저장소에 되므로, 로컬 PWA 버전과 진행 상황이
  공유되지 않는다(별개의 저장소).
- **인코딩 버그 발견 및 수정**: 첫 빌드에서 헤드리스 스크린샷으로 확인했더니 한글이
  전부 깨져 나왔다(`?`/네모 박스). 원인 추적 결과 아티팩트는 `<!DOCTYPE>`·`<head>`
  없이 본문 조각만 작성하는 구조라 `<meta charset="UTF-8">`이 빠졌고, 로컬 테스트 서버가
  `Content-Type` 헤더에 charset을 안 실어 브라우저가 인코딩을 잘못 추측한 것이 원인이었다
  (실제 raw 파일 바이트는 처음부터 정상이었음 — `grep`으로 원문 대조해 확인). 콘텐츠
  최상단에 `<meta charset="UTF-8">`을 명시적으로 추가해 해결하고 재검증했다.
- 공유 방법: 아티팩트는 기본 비공개다. 페이지의 공유 메뉴에서 공개로 전환해야 카톡으로 보낸
  링크가 상대방 기기에서 열린다.

## 레벨(100단계) 곡선 2차 수정 — 시작 레벨 버그 + 완만도 조정 (7차, 2026-08-25)

- **버그**: 새 게임 시작(성도 12명)이 Lv.9로 표시됐다("새로 시작하면 lv.1부터 해야지"). 원인은
  기존 제곱 곡선(`min = round(1600*(i/99)^2)`)이 초반 레벨 임계값을 0~1명 수준으로 거의
  0에 수렴시켰기 때문 — Lv.2 임계값이 0명이라 시작 인원만으로 이미 Lv.9까지 통과해버렸다.
  `START_FLOOR=15`로 앵커를 고정해 수정, Node `vm` 계산으로 `members=12 → level=1` 확인.
- **후속 조정**: 오너가 "Lv.2는 성도 15명, 다음 레벨들도 점차 어려워지도록" 요청. 앵커 수정
  직후에는 Lv.1→2 간격만 15로 크고 그 다음 몇 레벨은 간격이 1~2로 급감했다가 다시 서서히
  커지는 불균일한 곡선이었다. `LEVELS`를 등차-증가 간격 방식(`gap`이 매 레벨 0.5씩 커지는
  누적 합)으로 다시 짜서 모든 레벨 구간이 끊김 없이 단조 증가하도록 했다. 검증값:
  Lv1=0, Lv2=15, Lv3=16, Lv20=114, Lv30=239, Lv50=639, Lv70=1239, Lv90=2039, Lv100=2514.

## GitHub Pages 공개 배포 — 로그인 불필요한 설치형 PWA (8차, 2026-08-25)

아티팩트 링크는 클로드 계정 로그인이 있어야 열려서("링크 들어가니까 클로드 로그인을
해야 하네") 완전 공개·로그인 불필요한 실제 웹 호스팅으로 전환했다.

- `gh auth login --hostname github.com --git-protocol https --web` 로 오너 GitHub
  계정(rnjswl821) 브라우저 device-flow 로그인(토큰이 채팅에 노출되지 않는 방식).
- 리포지토리 `rnjswl821/church-tycoon-pwa` 를 public으로 생성·전체 푸시
  (`gh repo create --public --source=. --remote=origin --push`).
- `gh api -X POST repos/.../pages -f source[branch]=main -f source[path]=/` 로 GitHub
  Pages를 main 브랜치 루트에서 바로 서빙하도록 활성화.
- **누락 발견**: `manifest.webmanifest`·`index.html`이 `icon-192.png`/`icon-512.png`를
  참조하고 있었는데 실제 파일이 처음부터 존재하지 않았다(설치 프롬프트가 아이콘 없이는
  뜨지 않거나 깨질 수 있는 문제). `tools/gen_sprites.py`에 `app_icon(size)`를 추가해
  48px 네이티브로 그린 뒤 정수배 확대(NEAREST)하는 방식으로 192/512 아이콘을 새로 생성.
- 배포 후 `gh api .../pages/builds/latest` 로 빌드 완료(`status: built`) 확인, 헤드리스
  크롬 스크린샷으로 실제 접속 시 게임이 정상 렌더링됨을(새 게임 Lv.1 시작, 새 길
  네트워크·그림자·울타리·화단 모두 반영) 확인.

**공개 주소**: https://rnjswl821.github.io/church-tycoon-pwa/ — 로그인 전혀 필요 없음,
카톡 등 어디로 공유해도 그대로 열린다. 모바일 브라우저에서 열고 "홈 화면에 추가"하면
아이콘이 생기는 설치형 PWA로도 동작한다(서비스워커 오프라인 캐시 포함 — 아티팩트
버전과 달리 진짜 정식 배포이므로 sw.js가 정상 등록된다).

- 이후 코드를 수정하면 `git add -A && git commit -m "..." && git push` 로 반영하면 몇 분 내
  Pages에 자동 재배포된다(별도 빌드 설정 없이 정적 파일 그대로 서빙).

## 목회타이쿤 대규모 확장 (8차, 2026-08-25)

전체 설정 리뷰(내가 진행) 후 오너가 "1-7 모두 진행"을 확정하고, 이어서 여러 굵직한 신규
요청이 연달아 들어와 한 라운드에 함께 반영했다.

**리뷰에서 나온 실제 문제 수정**
- 예배당 최대 레벨(당시 Lv.5, 정원 1,600명)로는 100레벨 곡선(레벨100 ≈ 2,514명)에 물리적으로
  도달할 수 없었던 버그를 발견 — Node 시뮬레이션으로 "정원 다 채워도 최대 Lv.79까지만 가능"함을
  실측 확인 후, 예배당에 Lv.6를 추가해 우선 해소했다(이후 1만명 확장 때 Lv.8까지 더 늘림).
- 서비스워커 캐시가 실제 배포(GitHub Pages) 이후에도 안 올라가고 있던 문제 — 캐시 버전을
  v5→v7로 갱신하고 신규 스프라이트(울타리·화단·예배당 Lv.6~8)를 사전 캐시 목록에 추가했다.
- 부교역자 후보자 이력서를 새로고침할 방법이 없던 문제 — "다른 후보 보기" 버튼 추가.
- git 커밋 작성자 아이덴티티가 자동 추정값(호스트명 기반)으로 잡혀 있던 문제 — 로컬 저장소
  git config만 실제 GitHub 계정(rnjswl821)에 맞게 수정(과거 커밋 이력은 재작성하지 않음).
- 직분자 임기 만료가 로그 한 줄로만 남고 대시보드에서 놓치기 쉬웠던 문제 — 대시보드에 상시
  "직분자 현황"(장로/집사/권사 N/최대) 카드를 추가.
- 봉사자 자연증가·지역신뢰 동역학을 Node 시뮬레이션으로 실측 검증 — 사역만 켜고 아무 투자도
  안 하면 지역신뢰가 0으로 수렴해 성장이 멈춘다는 걸 확인(입소문 항 재설계로 아래에서 함께 개선).
- (검토만 하고 보류: OneDrive 동기화 폴더 안에 `.git`이 있는 구조 자체는 오너의 기존 결정
  [[project_automation_coaching_code_project_location]]을 존중해 그대로 유지.)

**신규 기능 — 시간 가속권 3종**
`BOOST_ITEMS`(소·중·대)를 추가했다. 성장 단계(TIERS)가 오를 때마다 자동 지급되고(초반 소,
후반 대), 운영 재정으로 '행사' 탭에서 직접 구매도 가능. 사용하면 20~30분간 자동진행 배속이
2~5배로 빨라진다(setInterval 고정 대신 매 틱마다 재스케줄하는 방식이라 사용 즉시 다음 틱부터
바로 빨라짐). 동시에 하나만 활성화된다.

**최대 1만명 교회까지 성장 가능하도록 밸런스 재설계**
Node 시뮬레이션으로 기존 성장식의 근본 한계를 발견했다 — 신규 유입(`visitors`)이 성도수와
무관한 "고정값"인데 이탈(`churn`)은 성도수에 "비례"하는 구조라, 지역신뢰·정착률을 아무리
극대화해도 특정 인원(약 800~1,100명)에서 수학적 평형점에 도달해 더는 못 자라는 구조였다.
`wordOfMouthRate` 항을 추가해 지역신뢰가 높을수록 "성도가 성도를 부르는" 입소문 유입이
성도수에 비례해 붙도록 재설계했고, 지역신뢰가 낮으면 이 항이 이탈률 하한(0.006/주)을 못
넘어서 여전히 정체되도록 해서 "시설만 늘려서는 못 크고 반드시 지역신뢰 투자가 필요한" 난이도
구조를 유지했다. 레벨 곡선(`GAP_GROWTH` 0.5→2.0, 레벨100 ≈ 9,600명대)과 예배당을 Lv.8(정원
10,500명)까지 확장해 맞췄다. Node로 두 시나리오 모두 실측: 최소 투자(사역 3개만)는 3,000주
동안 40명대에 머물렀고, 전면 투자(사역+부서 전부+건물 순차 업그레이드)는 약 1,234주 만에
Lv.100·성도 1만 명에 도달했다.

**신규 이벤트 3종 — 대형교회 규모의 어려움**
"성도수가 제자리걸음"(지역신뢰 저조 경고), "재정 운용 의혹"(스캔들 대응), "내부 분열의
조짐"(성도 1,000명 이상 전용 — 대응에 따라 실제로 상당수 성도가 이탈할 수 있는 고위험
이벤트)을 추가해 교회가 커질수록 새로운 종류의 어려움을 만나고 풀어가도록 했다.

**시작 화면 — 스플래시 로고 + 게임 소개**
링크로 처음 들어오면 로고 스플래시(1.4초 또는 탭하면 바로 넘어감)가 뜨고, 처음 실행하는
사용자에게만 게임 소개 확인창(브라우저 링크 공유 방식 안내 포함)을 보여준 뒤 게임을 시작한다.
기존 저장 데이터가 있는 재방문자는 스플래시만 잠깐 보고 바로 이어서 한다.

**절대 시간 표기**
기존 "개척 00년 00개월"(상대 나이)과 별개로, 실제로 게임을 시작한 달력 날짜(`gameStartDate`)를
기준으로 경과 주 수만큼 흘린 게임 속 달력 날짜(YYYY.MM.DD)를 상단에 함께 표기한다.

**용어·속도 조정**
"운영기금"→"교회 재정"으로 전면 변경. 자동진행 기준 속도를 "10분=게임 속 1개월"에서
"5분=게임 속 1개월"로 2배 가속(오너 지시).

## 직분자 임기 오류 수정 — 실제 고신헌법 확인 후 반영 (9차, 2026-08-25)

오너가 "직분자 임기는 헌법을 따라서 하고, 내가 전에 말했던 2년 임기는 봉사자라고" 지적.
게임 코드가 그동안 장로/집사/권사(직분자)를 "임기 2년 후 봉사자로 자동 복귀"하는 것으로
잘못 구현하고 있었고, 근거로 인용한 "윤번 시무 규정(제69조)"도 오인용이었다.

`04 지원/00 자비스/01 행정팀/고신헌법 2부 관리표준_전문.md`을 직접 열어 제63~84조를 재확인한
결과:
- 장로·집사는 **항존직**, 권사는 **항존직에 준하는 직분** — 셋 다 한번 임직하면 **정년(만 70세,
  제30~38조)까지** 계속 시무하는 게 원칙이며, 고정된 "임기 N년" 개념 자체가 헌법에 없다.
- 제69조(휴무장로)는 "당회가 (원한다면) 자체적으로 정하는 윤번 시무규정"에 관한 조항일 뿐,
  전 교단에 적용되는 고정 2년 주기가 아니다. 또한 "휴무"에 들어가도 장로 신분은 유지되며
  "봉사자로 돌아간다"는 개념이 아니다 — 완전히 잘못 인용했었다.

수정 내용: `processOfficerTerms()`(2년 경과 시 자동 만료→봉사자 전환)를 코드에서 완전히
제거하고, 직분자 설명 문구도 "정년까지 계속 시무" 방식으로 정정했다. Node 시뮬레이션으로
300주(5.7년)가 지나도 임직된 직분자 수가 그대로 유지됨을 확인. `state.officers[key]`의
임직 주차 배열 자체는 남겨뒀다(향후 정년 70세 모델링에 재사용 가능).

참고: 이번에 "봉사자"에 2년 임기 개념을 적용해달라는 요청은 아니었다(오너는 과거 발언의
소속을 정정한 것) — 봉사자는 여전히 단순 합산 자원(숫자)으로 남아 있고, 별도 순환제 기능은
이번 라운드에 추가하지 않았다.

**자동진행 속도 추가 조정**: "5분=1개월" 방식을 폐기하고 "1분=게임 속 1주"로 단순화(오너 지시).

## 저장 파일 내보내기·불러오기, 건물 업그레이드에 성도수 조건 추가 (10차, 2026-08-25)

**저장 관리**: "일반 모바일게임처럼 저장 기능도 있으면 좋겠다"는 요청으로 '기록' 탭에
내보내기(JSON 다운로드)·불러오기(파일 선택→확인창→덮어쓰기) 기능을 추가했다. `loadGame()`의

**주의**: 아티팩트(claude.ai) 미리보기는 페이지가 직접 파일 다운로드를 트리거하는 걸 보안상

아티팩트 게시 시 실제로 "다운로드 링크가 뷰어에겐 아무 동작도 안 한다"는 경고를 받았다.

**건물 업그레이드에 성도수 조건 추가**: 오너 지시 — "예배당과 교육기관을 업그레이드 할 때는
금액으로만 되지 않고 조건 정원 수가 있도록. 정원수는 효과가 되어서는 안됨." 즉 성도수 임계값은

`BUILDINGS.sanctuary`/`education`의 각 레벨에 `reqMembers`(자금과 별개로 요구되는 최소 성도수)를
추가했다(친교실·주차장은 지시 대상이 아니라 기존처럼 자금만으로 업그레이드).

- 예배당: Lv.1은 오너가 제시한 그대로(정원 40명·1,200만원). Lv.2 이상은 "직전 레벨 정원의
  90%"를 조건으로 잡았다 — **처음엔 "직전 레벨 정원과 100% 동일"로 구현했다가 Node
  시뮬레이션에서 실제 소프트락(영구 정체)을 발견해 수정**했다: `visitors = min(계산값,
  roomLeft+2)`로 정원 근접 시 유입이 강하게 눌리는데, 조건을 정원과 똑같이 잡으면 "정원을
  꽉 채워야 다음 레벨 조건이 열리는데, 정원에 가까워질수록 유입이 눌려 마지막 몇 명을 못
  채우는" 순환 정체가 실측 20,000주 동안 재현됐다(정원 800에서 797명에 붙박이). 조건을
  직전 정원의 90%로 낮추자(여유 10%) 같은 시뮬레이션이 1만 명(레벨100)까지 정상 도달했다
  (1,234주, 소프트락 발견 전과 동일한 속도로 복귀).

  Lv.4=`EVENT_TIER_TREE`(300명) — 기존 이벤트 해금 상수를 재사용해 새 매직넘버를 늘리지 않았다.
- 조건 미충족 시 건물 카드에 "🔒 성도 N명 이상 필요(현재 M명)" 잠금 표시가 뜨고 업그레이드
  버튼이 비활성화된다.

## 목회방향 세팅 기능, 접고펼치기 UX, 시간 계산 버그 수정 (15차, 2026-08-26)

**목회방향 세팅**: 오너 지시 — "항목 5개, 항목당 선택지 4개, 선택한 목회 방향에 따라 교회

스타일 5개 항목을 만들고 각 4택(총 20개 선택지)을 뒀다. 사역·건물처럼 돈으로 사는 게
아니라 비용 없이 매주 계속 적용되는 지속 효과이며, 언제든 다시 바꿀 수 있다. 다른 4택
시스템들과 같은 원칙으로 모든 선택지가 오르는 값과 내리는 값을 함께 가져 정답이 없게
설계했다(`PASTORAL_DIRECTIONS`, `computeModifiers`에서 매주 반영). Node로 두 항목을
동시에 설정했을 때 효과가 정확히 합산됨을 확인했다.

**접고펼치기(collapsible) UX**: 오너 지시 — "교적부는 평소 접혀 있다가 펼쳐지게, 다른
항목도 적용 가능한 곳엔 적용." 재사용 가능한 `collapsibleHeader()` 헬퍼 함수를 만들어
교적부(기본 접힘)·역대 행사 보고서(기본 접힘)·목회방향 5개 항목(기본 접힘)·지난 발자취
(기본 펼침 — 그 탭의 주 용도라 접어두면 오히려 불편해서 예외)에 적용했다.

**시간 계산 버그 수정**: 오너가 "개척 1년도 안 됐는데 교회 등록 11년차 성도가 있다"는
실측 오류를 발견 — `generalMemberProfile()`의 등록년차가 교회 자체의 실제 나이와 무관하게
순수 난수로만 계산되고 있었다. 성도 개인 나이뿐 아니라 **교회가 실제로 존재해온 기간**도
함께 상한으로 걸어(`churchAgeWeeks` 인자 추가) 개척 초기엔 모두 "등록 0년차"(미표시)로
나오도록 고쳤다. 30주(1년 미만) vs 780주(15년) 두 시나리오로 Node 검증.

**"오래 섬겨온" 계열 이벤트 재조정**: 게임 속도가 이번 세션 동안 여러 차례 빨라지면서

일러 보인다는 지적 — 5개 이벤트(특별한 헌신·결혼식 요청·상을 당한 가정·어른의 조언·유산
기부) 모두 최소 5년(주 260)으로 상향해 통일했다.

**기타**: 자동진행 버튼 문구 "시간이 흐르는 중"→"은혜가 흐르는 중".

## 직분자 임직 절차를 헌법대로 — 후보 추천·공동의회 투표 (16차, 2026-08-26)

## 건물 모양 변화 (18차, 2026-08-26)

오너 지시 — "건물 업그레이드 시 크기만 변하는 게 아니라 모양도 변화. 현실적인 모양으로."
자체 점검 결과 예배당(`sanctuary`)은 이미 레벨별로 첨탑·양쪽 익랑·슬레이트 지붕이 늘어나며
모양이 바뀌지만, 교육관(`education`)과 친교실(`fellowship`)은 5단계 모두 같은 지붕 형태를
크기만 키운 복제품이었다(깃발·책 표지판 등 소품만 추가). 두 함수를 완전히 새로 그렸다.

- **교육관**: 0단계 임시 교실 한 칸(트레일러) → 1단계 종탑 있는 박공지붕 단층 학사 →
  2단계 평지붕 2층 블록(깃발) → 3단계 ㄱ자형(2층 본관+단층 별관, 연결통로) + 그네 놀이터 →
  4단계 대형 교육관(본관+별관 모두 2층, 중앙 시계탑, 놀이터). 5단계 전부 실루엣이 다르다.
- **친교실**: 0단계 벽 없는 삼각 캐노피 천막(피크닉 테이블) → 1단계 소박한 박공지붕 단칸
  홀 → 2단계 줄무늬 어닝+컵 사인 카페형(기존 매력 포인트 그대로 유지) → 3단계 우진각지붕
  2층 친교관+야외 테라스 → 4단계 대형 커뮤니티홀(주방동 배기관+김, 야외 데크+테이블
  2개+조명줄). 처음엔 천막 캐노피를 줄무늬 폴리곤으로 그렸다가 톱니(불꽃)처럼 보이는
  렌더링 버그를 발견해, 단색 삼각 지붕+접힘선 텍스처로 다시 그렸다.
- 파일명(`education_0~4.png`, `fellowship_0~4.png`)은 그대로라 `sw.js` 자산 목록 수정은
  불필요, 캐시 버전만 v18로 올려 클라이언트가 새 PNG를 받도록 했다.
- 익랑·별관·놀이터가 붙어 좌우 폭이 비대칭으로 늘어나는 3~4단계도, 씬 렌더링이 이미지
  전체 폭 기준으로 중앙 정렬(`cx - im.width/2`)해 배치하는 방식(`sanctuary`의 양쪽 익랑과
  동일한 방식)이라 별도 코드 수정 없이 잘림 없이 배치됨을 헤드리스 크롬 스크린샷으로
  확인했다.

## 가로모드 스탯바 클리핑 버그 수정 (19차 후속, 2026-08-26)

오너가 실기기(아이폰 17 Pro)에서 가로모드로 켰더니 좌측 스탯 카드 5개 중 "교회 재정" 한
줄만 하단에 걸쳐 보이고 나머지 4개(성도수·신앙지수·지역신뢰·봉사자)가 통째로 안 보인다는
스크린샷 두 장을 보내옴.

원인은 CSS Grid의 잘 알려진 함정이었다 — `.stat-bar`가 놓인 4번째 행을 `1fr`로 잡아뒀는데,
그리드 아이템의 기본값 `min-height: auto`가 "내용물 높이보다 더 줄어들 수 없다"를 뜻해서,
씬 캔버스(1~2행 자동 높이) + 스탯 5줄(내용 그대로의 높이)을 합친 실제 필요 높이가 `100dvh`를
넘는 순간 `1fr` 트랙이 찌그러지는 대신 그리드 전체가 뷰포트 밖으로 흘러넘쳤다. 게다가 바깥
스크롤을 `html, body { overflow: hidden }`으로 막아둔 상태라, 넘친 부분은 스크롤도 안 되고
그냥 화면 밖으로 사라져 보이지 않는 상태가 됐다 — 시뮬레이터가 아니라 실기기 스크린샷이
아니었다면 놓치기 쉬운 유형의 버그.

- `.scene-wrap`·`.stat-bar`·`.tab-content`(전부 `1fr` 행에 걸린 그리드 아이템)에
  `min-height: 0`을 명시해, 내용이 넘칠 때 트랙이 실제로 줄어들고 각자의 `overflow-y: auto`가
  제대로 작동하도록 고쳤다. 헤드리스 크롬으로 900×360 뷰포트에서 `stat-bar.scrollHeight
  (118px) > clientHeight(92px)`를 직접 확인한 뒤, 강제로 `scrollTop`을 내려 5번째 스탯
  (봉사자)이 실제로 스크롤해서 보이는 것까지 스크린샷으로 검증했다.
- 재발 여지를 줄이려고 좌측 컬럼 폭도 `minmax(190px,300px)`→`minmax(180px,240px)`로 좁히고
  (씬 캔버스는 컬럼 폭에 비례해 커지므로 폭을 줄이면 높이도 함께 줄어든다), 탭 버튼·스탯
  카드 패딩/폰트도 더 압축해 대부분의 실기기 높이(대략 360~420px)에서는 스크롤 없이도 5개
  스탯이 한 화면에 다 들어오게 했다. `sw.js` 캐시 v20으로 갱신.

## 게임 제목 변경: 목회타이쿤 → 목양타이쿤 (20차, 2026-08-26)

오너 지시로 게임 제목을 "목양타이쿤"으로 변경. `<title>`·스플래시 화면·인트로 모달 문구

## PWA 매니페스트 orientation 고정 해제 (20차 후속, 2026-08-26)

가로모드(19차) 배포 후 자체 점검 중 발견 — `manifest.webmanifest`에 `"orientation": "portrait"`가
박혀 있었다. 브라우저 탭으로 열 때는 무해하지만, 홈 화면에 설치해 "앱처럼" 실행하는
경우(standalone display) OS가 이 값을 실제로 강제해서 폰을 눕혀도 세로로 고정된 채 안
돌아간다 — 방금 만든 가로모드 자체를 설치형 사용자는 아예 쓸 수 없게 되는 상황이었다.
오너에게 보고 후 승인받아 `"any"`로 변경. `sw.js` 캐시 v22로 갱신.
